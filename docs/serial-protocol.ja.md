# TURZX 3.5 インチ シリアルディスプレイプロトコル

本書は 3.5 インチ シリアルディスプレイ（`1A86:5722`）のシリアルプロトコルを説明します。WinUSB/Win207 デバイスではありません。Studio がホスト側で JSON テーマを描画し、CH340 シリアル経由で RGB565 の 1 フレームを送信します。

プロトコルは一方向です。Studio は応答を読み取りません。シリアル書き込みの成功は Windows がデータを受け取ったことだけを示します。

## デバイスとシリアルポート

- USB VID:PID は `1A86:5722` で、USB インスタンス名に `USB35INCH` を含みます。Studio はそのインスタンスの有効な `COM` ポートを探します。
- シリアル設定は 115200 bps、8 データビット、パリティなし、1 ストップビット、フロー制御なしです。DTR と RTS を有効にします。
- デバイスのキャンバスは 480 × 320 です。テーマは 480 × 320 または 320 × 480 のキャンバスを使用できます。
- フレームは再生開始時、テーマ切り替え時、方向切り替え時のみ送信します。連続ストリーミングは行いません。

## レジスタパケット

各転送は 6 バイトのヘッダーで始まります。X、Y、EndX、EndY は 10 ビット（0～1023）、レジスタは 1 バイトです。

| バイト | 内容 |
| --- | --- |
| 0 | X の 9–2 ビット |
| 1 | 7–6 ビットは X の 1–0 ビット、5–0 ビットは Y の 9–4 ビット |
| 2 | 7–4 ビットは Y の 3–0 ビット、3–0 ビットは EndX の 9–6 ビット |
| 3 | 7–2 ビットは EndX の 5–0 ビット、1–0 ビットは EndY の 9–8 ビット |
| 4 | EndY の 7–0 ビット |
| 5 | レジスタ番号 |

6 バイトを超えるペイロードを伴う場合、ペイロードバッファの先頭 6 バイトはヘッダーで上書きされ、有効なフィールドは 6 バイト目から始まります。6 バイト以下のペイロードは無視され、ヘッダーのみ送信されます。

## レジスタ

| レジスタ | 用途 | フィールド |
| --- | --- | --- |
| 255 | 接続確認 | 座標はすべて 0、ペイロードなし |
| 110 | ウェイク / バックライト | X = 255 − 輝度レベル。レベル 0 が最も暗く、255 が最も明るい。Studio はウェイク時に X = 0 を書き込む |
| 109 | ウェイク | 座標はすべて 0、ペイロードなし |
| 122 | ミラーモード | 16 バイトのペイロード。6 バイト目がモード（0 = 通常） |
| 121 | 方向 | 16 バイトのペイロード。6 バイト目が 100 + 方向タイプ（0–3）、7–8 バイトが幅、9–10 バイトが高さで、いずれもビッグエンディアン |
| 197 | フレーム開始 | ヘッダーの X = 0、Y = 0、EndX = 幅 − 1、EndY = 高さ − 1。続けて RGB565 ピクセルを送信 |

| 転送 | バイト |
| --- | --- |
| 接続確認 | `00 00 00 00 00 FF` |
| 輝度レベル 0（最も暗い） | `3F C0 00 00 00 6E` |
| 輝度レベル 255（最も明るい） | `00 00 00 00 00 6E` |
| 通常ミラー（16 バイト） | `00 00 00 00 00 7A 00 00 00 00 00 00 00 00 00 00` |
| 横画面 方向 2、480 × 320（16 バイト） | `00 00 00 00 00 79 66 01 E0 01 40 00 00 00 00 00` |
| 480 × 320 のフレームヘッダー | `00 00 07 7D 3F C5`、続けて 307,200 バイトのピクセル |

## 起動シーケンス

1. シリアルポートを開き、約 100 ms 待ちます。
2. レジスタ 255 を送信します。
3. 約 100 ms 待ち、レジスタ 110 と 109 に 0 を書き込みます。
4. 約 100 ms 待ち、ミラーモード 0 を設定してから方向を設定します。
5. 約 500 ms 待ち、目標の輝度を書き込みます。
6. レジスタ 197 のヘッダーを送信し、約 10 ms 待って RGB565 フレームを送信し、さらに約 10 ms 待ちます。

待ち時間は Studio の現在の実装に合わせています。ファームウェアによっては別のタイミングも許容されます。

## 方向

タイプ 0–3 はファームウェアの 4 方向に対応します。横画面テーマは既定でタイプ 2、反転時はタイプ 3 を使用します。縦画面テーマはタイプ 0 と 1 を使用します。Studio はこのディスプレイで 0° と 180° のみ提供します。

## フレームデータ

ピクセルは RGB565 で、上から下、左から右の順に並び、行間のパディングはありません。各ピクセルは 2 バイトで、下位バイトが先です（リトルエンディアン）。480 × 320 の 1 フレームは 307,200 バイトです。115200 8N1 では 1 フレームの送信に約 27 秒かかるため、このインターフェイスは静的なテーマ表示向けで、ライブ動画には適しません。

## テーマファイル

- Studio は JSON 形式の `.data` のみを読み取ります。旧形式のバイナリ `.data` は拒否されます。
- `backImg` は必須で、base64 PNG を格納します（既定テーマでは `backImg.png`）。任意のフィールドとして `osdImg`、`osdWithFontBack`、`groupList`、`barList`、`archList`、`tipList` があります。
- `isLanscape` は元のテーマファイルの綴りをそのまま使用します。キャンバスは 480 × 320 または 320 × 480 である必要があります。
- テキスト、バー、円弧、画像は Studio がホスト側で描画します。値はテーマファイルから取得し、項目テキストが空の場合はプレースホルダーのサンプル値を使用します。リアルタイムのセンサー値は読み取りません。
- Studio には横画面の既定テーマが 3 つ同梱され、いずれも 480 × 320 です。

## 制限

- Studio は読み取りチャネル、応答、再試行を使用しません。シリアル書き込みエラーだけが転送結果の通知です。
- 暗号化やコマンドキーはありません。
- このインターフェイスは、デバイス内ストレージ、H.264、レイヤー、時計、デスクトップモードを提供しません。
- 一度に 1 フレームだけを転送し、複数フレームを交互に送らないでください。

デバイスの認識、Studio での輝度と方向の操作は[互換性記録](compatibility.md)（英語）を参照してください。
